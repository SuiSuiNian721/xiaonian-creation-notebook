# 模块 16 · 生成成品（角色卡 · 必经）
> 概括：把手写源编译成酒馆能载入的成品卡（数据与 PNG），构建前自动先跑一遍体检。

## 何时进入
15-质检 双门通过之后。把 `src/` 编译成酒馆能读的成品。

## 这一步产出什么
跑 `node tools/card.mjs build <卡名>`（或 studio 的「生成成品」按钮）。它会**先自动跑一遍 check**（有错直接抛、不产出），通过后写出：
- `dist/<卡名>/card.json`（chara_card_v2 数据）；
- `dist/<卡名>/card.png`（把卡塞进 PNG 的 chara 块；底图用 `original/*.png`，没有就用占位图）。
并在 `.card/state.json` 记下本次 srcHash。**`dist/` 是产物，禁止手改。**

## 改完要重打
src 一旦再改动，`list` 会显示"需重新build"——交付前先重建，别发旧产物。

## 助手怎么做
- build 后确认 `dist/<卡名>/` 两文件都在、无报错。
- 想要带图的成品卡：先请用户把底图放进 `cards/<卡名>/original/`（你不写酒馆目录），再 build。
- 交付话术固定带一句：**"已通过 check/build，尚未真机验证"**——是否好用由用户在酒馆里验收。

## 用版本意识避免交错

生成成品前确认当前选中的卡、最新修改时间与准备交付的产物属于同一张卡。比如刚改过开场称呼，却把昨天的 PNG 当新版本导入，用户会以为修改没有生效。助手要以构建后的文件和 `list` 状态核对是否仍显示「需重新build」，一旦源文件再变动就重新构建。

交付说明写清本次改了什么、两道静态门的结果、数据和 PNG 的位置，以及尚需在酒馆里观察哪些互动。图片底图由用户提供并确认；占位图只证明卡数据可构建，不等于画面已经符合创作要求。

## 完成标准
`dist/<卡名>/card.json` 与 `card.png` 均已生成、build 无错；成品已包含 src 的最新改动；已明确告知"未真机验证"。

## 红线
**绝不写酒馆安装目录**（如 `F:\SillyTavern-1.15.0\`）——产物由用户手动载入；不手改 `dist/`；证据分层不越级（源码 → check/build → 真机 → 用户验收，上层不冒充下层）。

## 收尾
成品生成即本卡工作流结束。把进度落到卡根 `创作说明.md`（当前状态 / 已确认决定 / 待真机验收项），更新 `workflow.json` 的 `stage`/`done`，方便下次续接。
