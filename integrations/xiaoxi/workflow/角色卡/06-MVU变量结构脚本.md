# 模块 06 · MVU变量结构脚本（角色卡 · 按需，用 `mvu.mjs`）
> 概括：MVU 第一件：把变量定义编译成 Zod4 结构脚本，随卡载入注册，约束 stat_data 的形状（类型/枚举/默认值/剔除未声明字段）。

共用技术口径见 `workflow/MVU共用规范.md`；变量定义、计算职责、回流、显示与验收按该规范执行。

## 何时进入
05 之后。这张卡要**跨回合记住并更新状态**（好感、剧情标记、持有物等）时才做；纯对话卡跳过 06–10 整组。
MVU = MagVarUpdate 一类**外部变量扩展**（不是酒馆自带）：模型每轮用 JSON Patch 描述变量怎么变，扩展解析写进 `stat_data` 再回注。装没装、好不好看**必须用户真机验收**。

## 这一步产出什么
- **变量结构脚本**（Zod4）：`node tools/mvu.mjs gen <定义.json> --card <卡名>` 生成并写入 extra.json 的 tavern_helper 角色脚本。
- 口径：`z` 与 `_` 全局可用**勿 import**；用 `z.coerce.number()`、`.prefault()`、`.transform(v => _.clamp(v, lo, hi))`、`z.record(键, 值)`；结尾 `$(() => registerMvuSchema(Schema))`。`_` 前缀表示模型不可改；派生值仍须由 schema 或脚本明确计算。
- 这份 schema 是**运行时真会跑的约束**，不只是给作者看的契约。

## 研究样本：判断变量值不值得存在

先让用户讲一处「下一轮必须记得，故事才接得上」的情境。若角色把钥匙交给玩家，持有者状态可能值得记录；若她只是刚说了一句笑话，通常留在对话即可。再问每个字段谁来更新、谁会读取、是否需要显示。世界书写角色稳定的性格，变量只写会变的当前状态，避免把同一件事复制成两套真值。

例如「愿不愿带路」可以是布尔值；只有用户明确需要关系细微起伏时，才把它设计成有范围的数值。示例用于解释取舍，不预设这张卡一定需要好感度。确定结构后，将生成脚本、初值与之后的更新规则按同一份定义核对，防止字段只在其中一处出现。

## 助手怎么做
- 先和用户定变量组：每组哪些字段、类型、范围、默认值；宁少勿多，每个都问"剧情会用它做决定吗"。
- 定义 JSON 里可带 `imports`（外置手机等扩展 URL），一并生成 import 角色脚本。

## 引导与确认流程

1. 先用大白话说明本模块要解决什么、结束时会得到什么，不从工具命令或术语开始。
2. 读取已有 `src/` 与已确认计划，跳过用户已经回答的内容；每轮最多追问两三个与当前缺口直接相关的问题。
3. 用户卡住时给 2–3 个方向，并说明各自会怎样影响体验；示例必须标明是启发，不得自动进入正式内容。
4. 动手前在对话中展示完整待确认稿：正文或结构、目标文件、世界书条目与侧车配置、脚本/正则改动及外部依赖。明确列出仍属待定、不写入的内容。
5. 只有用户明确确认当前稿可以写入后才修改 `src/`。涉及世界书时同时遵守 `workflow/世界书写入指南.md`；用户要求调整时先改草稿并重新确认受影响部分。
6. 写入后按 UTF-8 回读，运行本模块规定的检查，汇报实际文件和未验证项；未确认、未写入或检查失败时不得标记完成或推进 stage。
## 完成标准
定义 JSON 定稿；schema 角色脚本已随 `--card` 写入 extra.json；diagnose「角色脚本」无 error；已告知真机验收。

## 红线
schema 不写卡身；不执行卡内脚本；MVU 扩展安装与否由用户真机确认。
