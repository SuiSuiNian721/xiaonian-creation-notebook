# 模块 08 · MVU变量更新规则（角色卡 · 按需）
> 概括：MVU 第三件：[mvu_update] 规则条目——教模型每轮用 JSON Patch 描述"哪些变量怎么变"；patch path 不带 stat_data 前缀。

共用技术口径见 `workflow/MVU共用规范.md`；变量定义、计算职责、回流、显示与验收按该规范执行。

## 何时进入
07 之后。

## 这一步产出什么
世界书条目 `[mvu_update]变量更新规则`（常驻或由已验证的规则路由加载；顺序不代替触发）：
- **何时更新**：哪类剧情动作触发哪组变量（对话/赠礼/冲突/时间推进）。
- **怎么更新**：使用与输出格式一致的 `add/replace/remove/move`；**path 不带 `stat_data.` 前缀**（如 `/属性/好感度`），与 EJS/状态栏读变量的 `stat_data.` 前缀相反。
- **幅度与边界**：单次增减的合理范围；派生量（`_` 前缀）禁改。

- **条目配置**：`[mvu_update]变量更新规则`，确保更新端能加载；插入位置与深度按实际预设验证，顺序 200 不代替触发条件。

## 研究样本：事件、知情与变化幅度

写规则前挑三种回合：明确改变关系的一次行动、角色尚不知情的一次行动，以及只是寒暄的普通回合。例如玩家替角色保守秘密且角色知道，信任可以按已商定幅度变化；若角色毫不知情，不因读者知道这件事就让她的信任凭空上涨；寒暄可以完全不改状态。这样可以检验规则是否写清「何时不更新」，避免每轮机械涨数。

示例补丁必须使用 schema 中真实存在的字段，且与本卡选定的操作方言一致。先用自然语言解释变化原因，再核对 patch 路径和边界；不要把临时剧情事件逐条积压成永久变量，也不要因输出格式示例而误以为每回合都必须制造变化。

## 助手怎么做
- 规则写成"情境 → 操作"的短句清单，配一个完整 patch 示例；不写抽象条款。
- 与 06 的 schema 对齐：规则里出现的字段必须都在 schema 里声明。

## 引导与确认流程

1. 先用大白话说明本模块要解决什么、结束时会得到什么，不从工具命令或术语开始。
2. 读取已有 `src/` 与已确认计划，跳过用户已经回答的内容；每轮最多追问两三个与当前缺口直接相关的问题。
3. 用户卡住时给 2–3 个方向，并说明各自会怎样影响体验；示例必须标明是启发，不得自动进入正式内容。
4. 动手前在对话中展示完整待确认稿：正文或结构、目标文件、世界书条目与侧车配置、脚本/正则改动及外部依赖。明确列出仍属待定、不写入的内容。
5. 只有用户明确确认当前稿可以写入后才修改 `src/`。涉及世界书时同时遵守 `workflow/世界书写入指南.md`；用户要求调整时先改草稿并重新确认受影响部分。
6. 写入后按 UTF-8 回读，运行本模块规定的检查，汇报实际文件和未验证项；未确认、未写入或检查失败时不得标记完成或推进 stage。
## 完成标准
规则条目落世界书；patch 示例 path 无前缀、字段与 schema 一致；diagnose「运行时接线」无 error。
