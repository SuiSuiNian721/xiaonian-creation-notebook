# 世界书写入指南（跨步共用参考 · 不是模块）
> 概括：世界书跨模块写入，但任何正式条目都必须经过“对话整理草稿 → 用户明确确认 → 写入与诊断”；讨论稿、AI 示例和未确认推测不得提前落盘。

## 何时读它
当前模块准备新增、修改或拆分世界书条目，或者需要判断触发词、常驻状态和顺序时读取。查完继续当前模块，不推进 `workflow.json` 的 stage。

## 先分清三类内容

- **已确认事实**：用户明确决定，可进入待确认成稿。
- **待研究想法**：仍有多个方向或用户尚未决定，只能留在对话或创作说明，不能写成正式设定。
- **AI 示例**：用于解释问题和打开思路，除非用户明确选择并改为自己的设定，否则绝不进入草稿或世界书。

## 每个模块的固定协作循环

1. **读取已有内容**：先看当前模块相关的 `src/`，避免重复条目和覆盖用户原文。
2. **引导取样**：根据用户已有内容追问，每轮最多两三个相关问题；先说明为什么问，再给一个与用户设定无关的小例子。
3. **整理待确认稿**：内容足够后，在对话中完整展示，不创建或改写文件。
4. **等待明确确认**：用户确认当前草稿可以写入，或逐项确认需要落盘的部分。模糊赞同、继续讨论和对示例的认可不算写入授权。
5. **按确认稿写入**：只写用户确认的正文和侧车配置，不顺手补充未讨论设定。
6. **回读与诊断**：按 UTF-8 回读，运行 `node tools/diagnose.mjs <卡名>`，处理世界书相关错误。
7. **汇报并推进**：说明实际写入的文件、检查结果和仍未确认的内容，再记录 artifact、标记模块完成并推进。

## 待确认稿必须展示什么

每条至少展示：

- 建议条目标题与所属世界书；
- 完整正文，不能只给摘要；
- `constant` 或触发式选择及理由；
- 触发式条目的 `keys`；
- `enabled` 与 `insertion_order`；
- 新建、修改、拆分或保持不动的文件范围；
- 仍属待定、不会写入的内容。

如果一次涉及多条，允许用户逐条确认。已确认条目可以写入，未确认条目继续停留在草稿状态；不能把“模块总体可以”自动扩大成对每条新增设定的授权。

## 玩家姓名与酒馆宏（写稿时必须遵守）

这里的宏是酒馆在组装提示词时替换的 `{{...}}` 占位符。制卡器中的待确认稿、源文件与成品保留宏原文，不提前换成本机用户的称呼；实际玩家名由酒馆当前选中的玩家人设决定。

- **世界书正文凡是指代玩家姓名，一律写字面 `{{user}}`**。角色描述、关系说明、开场白、对话示例和演绎指令里对同一玩家的姓名引用也遵守此规则，不把创作者姓名、聊天昵称或某次测试的玩家名写死。例如 `{{user}} 是这间书店的新管理员。`。自然的“你”“玩家”不需要机械改成姓名宏；用户明确要求保留的固定姓名或原文引用须单独说明并确认。
- `{{char}}` 只在确实指代酒馆当前角色时使用；固定 NPC 名、地点名和组织名照原设定保留。世界观卡的 `{{char}}` 可能只是世界卡的名字，不能用它代替书中所有人物。
- 宏保持半角双花括号和准确拼写，不翻译宏名，不在正式稿里添加转义反斜杠或提前求值。改已有条目时先在待确认稿中展示修改，不批量替换未确认的正文、文件名、UID、变量路径和触发词。
- 需要按玩家名触发的关键词可以使用 `{{user}}`，酒馆会先展开关键词再匹配；只在确实需要姓名触发时选用，不把它作为所有条目的通用触发词。触发方案仍须说明理由。

### 常用的酒馆原生宏

下表用于选择调用方式，不要求每张卡都使用。内容字段会展开宏；标题、文件名与变量键不应依赖同样的展开行为。

| 写法 | 读取或执行什么 | 使用边界 |
|---|---|---|
| `{{user}}` | 当前玩家人设的姓名 | 用于玩家姓名，不等于制卡时创作者的称呼 |
| `{{char}}` | 当前角色名 | 单个角色引用；固定 NPC 保留其名字 |
| `{{persona}}` | 当前玩家人设描述 | 这是设定正文，不是姓名 |
| `{{description}}` / `{{personality}}` / `{{scenario}}` | 角色卡的描述 / 性格 / 场景字段 | 按需引用，避免与既有注入重复，不在同一字段里自引用 |
| `{{mesExamples}}` / `{{mesExamplesRaw}}` | 格式化 / 原始对话示例 | 常用于提示词编排，不重复复制整套示例 |
| `{{group}}` / `{{groupNotMuted}}` | 群聊成员名 / 排除静音成员的成员名 | 群聊相关规则；不是任意世界书 NPC 清单 |
| `{{lastUserMessage}}` / `{{lastCharMessage}}` | 当前聊天最近的玩家 / 角色消息 | 按需读取聊天文本，不当作可靠的状态变量 |
| `{{getvar::变量名}}` / `{{getglobalvar::变量名}}` | 酒馆当前聊天 / 全局变量 | 不是 MVU 的 `stat_data` 路径，变量须已有正确来源 |
| `{{setvar::变量名::值}}` / `{{setglobalvar::变量名::值}}` | 写入酒馆聊天 / 全局变量 | 会改变状态；只用于明确设计的变量操作，不混入普通设定 |
| `{{random::选项一::选项二}}` | 每次解析重新随机选择 | 不用来保存应保持不变的人物设定 |
| `{{pick::选项一::选项二}}` | 在同一聊天、文本内容及宏位置下保持选择的随机项 | 文本/位置改变或重新抽取可变，不替代持久游戏状态 |
| `{{roll::1d20}}` | 掷骰结果 | 每次解析会掷骰；需要留存的结果另行设计 |
| `{{time}}` / `{{date}}` / `{{weekday}}` / `{{isodate}}` | 真实本地时间 / 日期 / 星期 / ISO 日期 | 不等于剧情世界的时间；剧情时间用已设计的状态来源 |

其他插入方式：`{{outlet::名称}}` 在提示词管理器或高级格式中插入同名 Outlet 世界书条目。它不能放进世界书正文、角色描述/性格/场景字段或作者注释中，也不支持 Outlet 内再嵌套 Outlet；不要把它当作世界书正文里的通用跨条目读取。

### 扩展调用与原生宏分开

- 本项目 MVU 变量列表已有 `{{format_message_variable::stat_data}}`：读取最新消息楼层的 `stat_data` 并格式化为 YAML；`{{get_message_variable::stat_data}}` 则输出 JSON。它们依赖酒馆助手宏功能，不是酒馆原生 `{{getvar::...}}`，不能互换。
- 酒馆助手还提供 `{{get_chat_variable::路径}}`、`{{get_character_variable::路径}}`、`{{get_preset_variable::路径}}`、`{{get_global_variable::路径}}`，分别读取聊天、角色卡、预设、全局存储的变量；对应 `format_..._variable` 形式用于格式化输出。先确定变量保存在哪一层，再选宏，不能只因名字里有“变量”就当作同一份数据。
- `<% ... %>` / `<%= ... %>` 是 EJS 模板语法，按当前 EJS 模块及已安装的模板扩展使用；不是姓名宏，不在制卡器中执行。
- 预设中的 `worldInfoBefore`、`charDescription`、`personaDescription`、`chatHistory` 等是提示词编排插槽的标识符，不应直接写成自创的 `{{worldInfoBefore}}` 等宏。宏名相似也不能据此假定行为相同。

写入前核对：玩家姓名引用是否保留 `{{user}}`；`{{char}}` 是否仅指当前角色；NPC 与标识符是否保持原样；引用的变量来源、扩展依赖与调用位置是否清楚。这些是写作核对项，现有 `check/build` 通过不能代替酒馆实际展开验收。

来源：SillyTavern 官方 [宏说明](https://docs.sillytavern.app/usage/core-concepts/macros/) 与 [世界书说明](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)，并对照本机 SillyTavern 1.15.0 的原生宏定义和世界书展开路径（2026-10-12）；扩展部分见酒馆助手官方 [宏说明](https://n0vi028.github.io/JS-Slash-Runner-Doc/guide/功能详情/酒馆助手宏.html) 与 [变量获取](https://n0vi028.github.io/JS-Slash-Runner-Doc/guide/功能详情/变量/获取变量.html)。完整原生宏清单可在酒馆输入 `/? macros` 查看；依赖扩展的用法还要核对相应扩展版本。

## 条目落点与侧车

每条 = `src/worldbook/<书>/NNN-<名>.md` + 同名 `.yaml`：

- `keys`：具体、专属的名字、别称、地名或术语；避免“世界”“时间”“角色”等泛词。
- `constant`：每轮确实需要才设为 true；默认优先按需触发。
- `insertion_order`：同时命中时的先后，数值越小越靠前。
- `enabled`：false 表示保留但不进入通常加载；InitVar 等程序读取条目按各模块约定处理。

## 写入后的评估

运行 `node tools/diagnose.mjs <卡名>`，重点处理：

- 启用且非 `constant` 的条目没有 keys；
- 正文为空；
- keys 含空字符串、泛词或跨条目冲突；
- 常驻 token 过高；
- EJS、脚本或其他条目仍引用旧名称；
- 同一设定在多个常驻条目重复，诱发模型反复强调。

## 完成标准

用户确认的正文与磁盘内容一致；每条触发方式有理由；诊断零错误，警告逐条处理或记录保留理由；未确认内容没有落盘；模块进度只在这些条件满足后推进。

## 红线

不以“先写进去再让用户改”代替确认；不把 AI 示例混成正式设定；不滥用常驻；不创建永不触发的死条目；不因整理格式而改写用户原意。

## 用完回到哪

回到当前模块继续。本文本身不是 stage，不单独标记完成。
