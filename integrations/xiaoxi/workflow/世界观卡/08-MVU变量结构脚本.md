# 模块 08 · MVU变量结构脚本（世界观卡 · 按需，用 `mvu.mjs`）
> 概括：MVU 第一件：把**世界刻度**的变量定义编译成 Zod4 结构脚本，随卡载入注册，约束 stat_data 形状。

共用技术口径见 `workflow/MVU共用规范.md`；变量定义、计算职责、回流、显示与验收按该规范执行。

## 何时进入
07 之后。这张世界卡要**跨回合记住并更新世界状态**（局势/季节/资源/阵营关系）时才做；静态世界跳过 08–12 整组。

## 与角色卡的差别
变量主体是**世界的量**而非个人好感：如 `局势.治安`、`资源.粮价`、`阵营.教会_商盟`。其余口径一致。

## 这一步产出什么
- **变量结构脚本**（Zod4）：`mvu.mjs gen <定义.json> --card <卡名>` 写入 extra.json 的 tavern_helper 角色脚本。
- 口径：`z`/`_` 全局勿 import；结尾 `$(() => registerMvuSchema(Schema))`；`_` 前缀表示模型不可改，公式必须由 schema 或独立计算脚本明确实现，不会仅凭命名自动计算。

## 研究样本：世界需要记住哪种变化

先从玩家能感知的后果选变量。若港口封闭会改变通行和贸易，「港口开放」可能是一项必要状态；若季节只是背景气氛，不需要每轮更新日期计数器。世界级数值要匹配世界级事件：一个小摊争执不应立刻改变整座城市的治安。助手可以用这些自造样本解释尺度，但不能未经确认把港口或治安写成用户世界的正式变量。

每个字段都问更新者、读取者和展示位置，明确其类型、范围、初值。特别核对从 01–05 设定里抽出的规则是否稳定：稳定世界法则仍在世界书，变量只存当前局势。结构脚本生成后还要沿初值、规则、回流链逐站检查，而不是只看脚本文件存在。

## 助手怎么做
- 先定"世界要记住哪几个量、范围与初始值"；每加一个都问"剧情会用它做决定吗"。
- 定义 JSON 可带 `imports`（外置手机等），一并生成 import 脚本。

## 引导与确认流程

1. 先用大白话说明本模块要解决什么、结束时会得到什么，不从工具命令或术语开始。
2. 读取已有 `src/` 与已确认计划，跳过用户已经回答的内容；每轮最多追问两三个与当前缺口直接相关的问题。
3. 用户卡住时给 2–3 个方向，并说明各自会怎样影响体验；示例必须标明是启发，不得自动进入正式内容。
4. 动手前在对话中展示完整待确认稿：正文或结构、目标文件、世界书条目与侧车配置、脚本/正则改动及外部依赖。明确列出仍属待定、不写入的内容。
5. 只有用户明确确认当前稿可以写入后才修改 `src/`。涉及世界书时同时遵守 `workflow/世界书写入指南.md`；用户要求调整时先改草稿并重新确认受影响部分。
6. 写入后按 UTF-8 回读，运行本模块规定的检查，汇报实际文件和未验证项；未确认、未写入或检查失败时不得标记完成或推进 stage。
## 完成标准
schema 角色脚本已写入 extra.json；diagnose「角色脚本」无 error；已告知真机验收。

## 红线
schema 不写卡身；不执行卡内脚本。
