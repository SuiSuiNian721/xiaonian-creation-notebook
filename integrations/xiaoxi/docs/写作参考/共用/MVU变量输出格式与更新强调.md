这一部分只规定模型怎样把状态变化交给扩展读取，不重新设计剧情。正文照常写给玩家，需要更新时再附合法的数据块。

### 第 1 步：确定本卡使用的更新协议

标签、操作名、路径写法和数组结构必须统一，不能把不同方言混在一张卡里。

> 小例子：同一张卡不能一部分使用点路径命令，另一部分突然改用另一套 JSON Patch 操作名。

### 第 2 步：把结构、规则和输出逐项对齐

输出中的每个路径必须存在，规则必须解释何时变化，没有变化时输出合法空数组。

> 小例子：港口从开放变成封闭时只修改对应字段，不把整段火灾叙述塞进更新数组。

### 第 3 步：只对真实错误增加强调

先收集漏块、标签未闭合或路径错误的实际样本，再增加一两条针对性提醒。预先堆叠重复命令会挤占剧情注意力。

> 小例子：若真机记录显示模型常把数字写成字符串，就针对该字段补一句类型提醒；没有证据时不堆叠“必须、严禁、再次强调”。

### 第 4 步：用三种回合检查

观察一次确实变化、一次完全不变化、一次发生多件事但只应改部分字段的回合，比较正文、更新块与保存结果。

> 小例子：分别测试“没有变量变化的闲聊”“魔力下降的施法”“新增道具后又移除”的回合，能覆盖空更新、数值更新和数组变化。

### 第 5 步：确认后写入

助手会展示输出协议和是否启用额外强调。你确认后才写入对应世界书与正则配置；静态正确仍不等于酒馆已经成功保存。

> 小例子：用户确认使用 RFC 6902 的 `add/replace/remove/move` 后，才写输出格式；不能在未确认时混入另一套 `delta` 方言。
