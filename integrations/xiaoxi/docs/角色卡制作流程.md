# 角色卡推荐制作流程（人机共读）

本流程说明一张角色卡如何从构思走到可导入产物。studio 对话上方「写作参考」打开的 `docs/写作参考/` 面向创作者，逐步说明写什么、怎么写并提供不同的小例子；`workflow/*.md` 面向你，规定你怎样提问、整理、确认、写入和检查。两套内容职责不同。

预设另见 `workflow/预设制作规则.md`。具体文件边界与交付门以 `AGENTS.md` 为准。

## 总路线

```text
自然确认本轮要写什么
  → 00 引导与模块规划
  → 世界观简介
  → 角色画像
  → NPC（可选）
  → 角色速览
  → 开场白
  → MVU / 界面等按需模块
  → check + 9 项诊断
  → build
  → SillyTavern 真机验收
```

每个内容模块内部都执行同一循环：

```text
读取已有内容
  → 小步提问与扩展思路
  → 在对话中展示完整待确认稿
  → 用户明确确认
  → 写入 src
  → UTF-8 回读与模块检查
  → 记录产物并进入下一模块
```

未确认、未写入或检查失败时，不把模块标记为完成。

## 0. 用自然对话确认本轮内容

开始写卡时，助手先读取当前模块、已有正文与已确认决定，再像制卡研究员做访谈一样自然确认：这轮具体写哪一部分，现有内容中哪些保持不动，以及先聊想法、整理草稿，还是在确认后正式写入。

用户不需要填写任务表格，也不需要理解工程术语。已经说清的内容直接复述，不再重复询问；只有会明显改变写作方向的信息缺失时，助手才一次追问两三个问题。

例如：“我先记一下：这轮我们补她从普通熟人走向朋友的过程，已有外貌和工作背景先保留。我会先整理关系变化的草稿给你看，你确认后再写进世界书。这样对吗？”

## 1. 建卡、导入与续接

- 新卡：studio 新建卡，或 `node tools/card.mjs new <卡名>`。
- 导入：studio 导入 PNG/JSON，或 `node tools/card.mjs import <文件>`。
- 已经拆分的卡继续修改 `cards/<卡名>/src/`，不重新 import 覆盖。
- 长项目先读卡根 `创作说明.md` 与 `.card/workflow.json`；已有决定不重新讨论。

## 2. 引导阶段只做规划

引导阶段先确认卡类型、核心体验、世界摘要、玩家入口和实际需要的模块。角色卡与世界观卡各走自己的轨道，可选模块没有体验需求时直接跳过。角色卡的世界摘要只保留理解人物所需的一小段背景；完整规则、地区、制度、经济与历史进入世界观卡轨道。

这一阶段不写正文。规划中区分：

- 已确认决定；
- 尚待研究的问题；
- 明确暂时不做的功能。

## 3. 页面参考与助手引导

用户在制卡模式对话上方点击“写作参考”，展开面板后打开详细写法，看到的是创作者版步骤。面板默认收起，用完可再收起，把空间留给对话。参考应帮助用户知道当前要写什么、从哪里开始、怎样判断写够了。

你本轮只读取当前 `workflow/<stage>.md` 与 `workflow/助手共用规则.md`，当前人格由程序提供；根据用户已有内容选择起点：

- 不要求用户重新回答已经写清的内容；
- 每轮最多问两三个相关问题；
- 用户卡住时给 2–3 个方向，并说明各自的体验影响；
- 例子只负责启发，不得自动混入正式设定；
- 用户说不知道或暂缓时记录待定，不用默认设定填满。

## 4. 人物画像的核心顺序

角色模块按以下顺序研究，并在最后回到性格核心复核：

1. 基础身份；
2. 性格核心的雏形；
3. 外貌与自我呈现；
4. 当下生活；
5. 仍在影响现在的过去；
6. 喜欢、讨厌与能力；
7. 关系怎样逐渐变化；
8. 具体情境中的反应；
9. 语言随关系和状态怎样变化；
10. 平时保持休眠的秘密、怪癖和标志物；
11. 整合检查与演绎边界。

人物资料描述倾向和可能原因，不是每轮必须展示的清单。当前事件、目标和关系优先；没有直接触发时，不主动回忆或解释创伤与过去。关系必须通过多次可观察经历变化。

详细步骤见 `docs/写作参考/角色卡/02-角色.md` 与 `workflow/角色卡/02-角色.md`。

## 5. 世界书跨模块写入

本项目把设定正文放进世界书，卡身保留开场与必要的薄锚点。世界书不是单独一步，而是在世界观、人物、NPC、速览、MVU 和部分界面模块中按需产生。

任何世界书写入必须先展示：

- 条目标题和完整正文；
- 所属世界书与目标文件；
- 常驻或触发选择；
- 触发词、启用状态和顺序；
- 待定且不会写入的内容；
- 新建、修改、拆分或保持不动的范围。

只有用户明确确认当前稿可以写入后才修改 `.md` 与同名 `.yaml`。详细规则见 `workflow/世界书写入指南.md`。

## 6. MVU 与运行时模块按需进入

需要跨回合保存状态时才使用 MVU。标准顺序是：

1. 变量结构脚本；
2. 初始变量；
3. 更新规则；
4. 变量列表与状态回流；
5. 输出格式与必要的更新强调；
6. 状态栏、EJS、小手机或同层 UI 等可选显示能力。

MVU、EJS 与界面没有 studio 生成面板，由你使用 `tools/mvu.mjs`、`tools/ejs.mjs` 和现有源码完成。生成前仍要展示结构、目标文件和依赖，确认后才写入。

## 7. 质检双门

第一道门：

```powershell
node tools/card.mjs check <卡名>
```

检查文件结构、必填项与侧车，必须零错误。

第二道门：

```powershell
node tools/diagnose.mjs <卡名>
```

当前共 9 项：基础字段、世界书、关键词冲突、token、八股、正则脚本、运行时接线、EJS 用法和角色脚本。诊断只读，不会替作者改正文。

对于用户手写人物内容，只指出具体矛盾、空泛标签或演绎风险，不擅自改成统一范文。

## 8. 生成成品与真机验收

检查通过后点击「生成成品」，或执行：

```powershell
node tools/card.mjs build <卡名>
```

产物位于 `dist/<卡名>/card.json` 与 `card.png`。`list` 显示“需重新build”时，旧产物不包含最新源码。

证据层级必须分开：

```text
源码已写入
  → check / diagnose 通过
  → build 成功
  → SillyTavern 真机运行
  → 用户验收
```

上一层不能代替下一层。工具不写 SillyTavern 安装目录，产物由用户手动导入。

## 9. 断点续接

卡片长期进度只写在卡根 `创作说明.md`。`workflow.json` 记录当前 stage、已完成模块、规划和产物索引，由受控接口或 CLI 管理，不手改。

新会话先复述当前进度、已确认决定与下一步。已经确认并写入的内容不重新开放，除非用户主动要求修改。
